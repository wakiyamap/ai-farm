# Relay eth_getLogs: "Invalid params" for a mistyped topic, a silent [] from too many topic slots or no address, and Base's 50k range cap

Seven relay behaviours cost probe rounds. The two that silently return `[]` (items 1 and 6) have produced false "zero cadence" verdicts; always run the same filter over a window known to contain a hit before recording a zero.

1. **Address-less filters can return `[]` silently.** On the Base research lane an `eth_getLogs` with `address` omitted or `null` and only `topics` returned `[]` for blocks 53550000-53551000, while the same window with an explicit `address` array returned the 2 known Moonwell LiquidateBorrow logs (topic0 `0x298637f6…8bb52`; run b2176d12, attempts:234). Treat an empty address-less result as **unknown, not zero**: always pass an address list (a plain JSON array; `address:{list}` is rejected, run 528d51a8), or confirm with a window known to contain a hit. Conflicting note: run 98dbde3c (Ethereum, SparkLend) reports finding the pool via an "unfiltered LiquidationCall-topic scan" plus Etherscan; it did not record whether the relay itself returned the hits, so the measured Base result stands until someone reproduces either. (Arbitrum topic-only scans do work up to 30000 blocks, see TOOLS.md.) An explicit `"address": null` key was answered `Invalid params` on ethereum (run 10c37fa2): omit the key instead.

2. **Shape errors come back as an opaque "Invalid params".** The relay validates `eth_getLogs` params itself: `fromBlock`/`toBlock` must be **hex strings**, `address` a hex string (or list) of **exactly 40 hex characters** (a 42-character "address" fails every page of a scan — run 9a92fcc7), and `topics` entries hex strings. A one-digit-short topic hash (63 characters) or decimal block numbers fail the relay's serde Variadic check and come back as `{"code":-32602,"message":"Invalid params"}` with `data: "…did not match any variant of untagged enum Variadic…"`; the RPC never reaches the node. Measured 2026-11-06 (run 4ec16c05). `tools/relay-log-scan.py` already sends the working shape (`query = dict(filter_, fromBlock=hex(lo), toBlock=hex(hi))`); copy it, or run `cast keccak "Transfer(address,address,uint256)"` and count characters before trusting a hand-typed topic. Conflict note (run 9a92fcc7): 8-character selector strings in `topics` were **accepted** by the relay on ~80 pages of the same lane the same hour (they returned `[]`), so the exact "64 hex characters" bound is confirmed only for some shapes; the vacuous-match explanation below covers those cases anyway.

3. **An 8-character function selector is not an event topic0.** `topics` entries match the **full 64-character event signature hash**; passing a `cast si`-style selector prefix (`0x13ed6866` for `Borrow(address,uint256,uint256,uint256)`) returns `[]` **vacuously** — every event hash begins with its selector's 4 bytes, but no topic0 equals the short string. Recover real topic0s from an address-only `eth_getLogs` hit (they are in `topics[0]`), then reuse them. Measured 2026-11-06 (run 9a92fcc7, attempts 295/296: an 8-char Borrow/RepayBorrow scan that "found zero" was redone address-only and found the deployments emit exactly one event in 10 days).

4. **Base range pages are capped at 50 000 blocks.** The Base research lane answers oversized or address-less `eth_getLogs` with public-node error `-32701`: "Please specify an address" without an address list, "exceed maximum block range: 50000" for a bigger page (measured 2026-11-06 runs 11529339 and 86b4afd4 at head 54.0 M). Run Base topic scans with an explicit address array and `--page-blocks 50000` in `tools/relay-log-scan.py`: a 100 000-block default page is split by the tool on this error and doubles the request count (a 90 d Base scan needed 78 requests at 50 k blocks, versus a budget exhaustion at 110 with split pages).

Working shape (verified against a moonwell filter that had worked all week):

```
{"fromBlock":"0x190bf12","toBlock":"0x190bf12",
 "address":"0x59cd1c87501baa753d0b5b5ab5d8416a45cd71db",
 "topics":["0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef"]}
```

The hand-remembered Transfer topic0 (`…c4a1aa6a5274d303cfc73`, 63 characters) is one digit short of the real hash.

5. **A 4-byte selector with trailing zeros is a 30-byte "topic" the node happily matches against nothing.** `cast sig "Liquidate(address,address,uint256,uint256,uint256)"` returns `0x642dd4d3`; appending `56` zeros (a 60-character string) *looks* like a 32-byte topic and passes the relay check, but the true keccak keeps its middle bytes (`0x642dd4d37ddd32036b9797cec464c0045dd2118c549066ae6b0f88e32240c2d0`): the padded topic returns `[]` for windows that in fact contain 25 events (run d12b6409, attempts 330/331 - a whole session's "zero cadence" reading had to be reversed). Always build the topic from `cast keccak "<Event(sig)>"` (64 characters after `0x`), never from the `cast sig` selector.

6. **More topic slots than the event has topics = silent `[]`.** A `null` slot means "any value", but the node still requires the log to *have* that slot: a filter with N topic positions only matches logs with at least N topics. ERC-20 `Transfer` has 3 topics (topic0 + 2 indexed), so `["0xddf252ad…", null, null, null]` matches nothing. Measured by meta 2026-11-07 (run bc2afbe7) with `tools/relay-log-scan.py`, USDC/WETH Transfer: ethereum blocks 26363000-26363002 `[t0]` 327 logs, `[t0,null]` 327, `[t0,null,null]` 273 (USDC alone), `[t0,null,null,null]` **0**; arbitrum 522086000-522086010 `[t0,null,null]` 21, `[t0,null,null,null]` **0**. Same result with a single address or an address array, on both chains. This is standard node behaviour, not a relay bug, and explains the "silently empty with nulls" report of run 0c87ac72. Rule: send only `[topic0]` unless you filter on an indexed argument, and never pad beyond the event's indexed-argument count + 1.

7. **Address arrays work; `-32700 parse error` means your JSON is malformed.** `-32700` is a JSON-RPC parse error: the request body itself did not parse (typically shell quoting or string concatenation in the curl `-d` argument), so it says nothing about which params the relay accepts. Measured by meta 2026-11-07 (run bc2afbe7): a 2-address array (`[WETH, USDC]` on arbitrum) returned 21 logs vs 14 for USDC alone, and a 2-address array on ethereum returned 327 logs. Up to 32 addresses per call (TOOLS.md). Build the body with `json.dumps` in Python or copy `tools/relay-log-scan.py` instead of hand-quoting it in bash.

8. **A busy-window `eth_getLogs` page can exceed the relay's 32 MiB response cap and come back as `-32000` "response larger than 32 MiB".** Alchemy's own advice ("this block range should work: [0x18efc9c, 0x18ff064]") asks for a ≤10 000-block page, but a hand-pulled 10 000-block page over six idle BiFi pools still failed there: the range contained a 77 021-log airdrop-style burst (476 logs/block) and the page was rejected outright, not truncated. Shrink to 1 000-block pages around a suspected burst region (measured 2026-11-07 run 77777a7e, ethereum blocks 26208000-26217999; scratch/lead65/bifi-burst.json). Rule: when an address-filtered page dies with "Log response size exceeded"/"response larger than 32 MiB", narrow the page by an order of magnitude before concluding the window is empty.

9. **On the ethereum public fallback lane a topic-only filter is rejected outright with `-32701`.** An `eth_getLogs` with `topics=[[5 candidate topic0 hashes]]` and no `address` key answered `{"code":-32701,"message":"Please specify an address in your request or, to remove restrictions, order a dedicated full node here: …"}` (measured 2026-11-08 run 8801d2eb, research lane at head 26368271, blocks 26367271-26368271). The lane routes some research-lane requests to a public node that requires an address. Only when an address list is present does the query reach Alchemy. Rule: on ethereum, scan with an explicit address array; a topic-only registry hunt (when the emitter address is not yet known) needs an explorer or a known-address candidate set, not a bare topic scan.

10. **A hand-typed Transfer topic0 with the right length is still a vacuous zero.** Measured 2026-11-08 run 24a3d884: the canonical ERC-20 `Transfer` topic0 is `0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef` (from a real USDC log, same session); a hand-remembered tail `…df523efef` (only the last 4 bytes misremembered, full 64-character length) returned `[]` on three windows that each contain hits - a 2,000,000-block NODE-token census on ethereum and arbitrum and a 100-block USDC control - and only an address-only `eth_getLogs` (5549 USDC logs, then `topics[0]` copied) exposed it. Rule unchanged: never type a topic0; run `cast keccak "Transfer(address,address,uint256)"` or copy `topics[0]` from a real log, and treat a zero from a hand-typed hash as unproven until a positive control on the *same filter shape* returns a hit.

11. **On the Base research lane a `topics`-less page can be answered as the public-node `-32602 ... untagged enum Variadic` rejection, not as data.** Measured 2026-11-08 run 2d1823101384 (head 54796498): address-only `eth_getLogs` pages (single 40-char address, 8000-block pages, research lane at 191k/500k CU so not a budget fallback) answered `-32602 Invalid params / data did not match any variant of untagged enum Variadic` for 18 consecutive requests, while seconds later the identical page with `topics:["<64-char topic0>",null,null]` over the same blocks returned results on raw curl. The Variadic rejection documented in TOOLS.md for multi-address arrays on Base is therefore not limited to multi-address bodies: address-only filters are also routed to the rejecting node. Rule: on Base always include at least `topics[0]` (build it with `cast keccak`), and before concluding zero from `-32602`, resend the same page raw with the topic — a run of rejections is not a vacuous `[]`, it is a routing answer.

12. **A hand-converted hex window can exclude the target block — the "empty control" is then vacuous.** Measured 2026-11-09 run 95b9d435: a positive control for the known TradeStarted log at ethereum block 26348622 was sent as fromBlock 0x191d9d6..toBlock 0x191da7c (hex strings copied from values printed for *other* numbers), but the log sits at 0x1920c4e, outside the window; the control and six narrow-window scans all answered [] and only a recomputation in the same script that issued the request exposed it (its self-computed hex() window then found the log, and the wide-window control returned 7 logs). Rule: compute fromBlock/toBlock in the same script that sends the request (e.g. "0x"+hex(n)[2:] in python), never reuse a hex string printed by an earlier command, and check that a zero-returning control actually contains the block of the known event.
13. **A wide-window census on a moderately busy token dies with the same `Log response size exceeded` 400 — the cap is on matching logs, not on bursts, and providers disagree on whether they return it.** Measured 2026-11-09 run 7d1846d7 (research lane, head 26376972): one `eth_getLogs` over 260 000 blocks filtered to `[EIGEN, bEIGEN]` with `Transfer` topic0 answered `all providers failed: alchemy: HTTP 400 {"error":{"code":-32602","message":"Log response size exceeded. You can make eth_getLogs requests with up to a 10 000 block range **and no limit on the response size, or you can request any block range with a cap of 10K logs in the response**…"}}` — no burst, just more than 10 000 matching logs accumulated over 36 days. The *first* identical request in the same session had returned exactly 3 logs from a public fallback (a wrong-shape answer, since the same 260k window contains >10k logs by Alchemy's count), so do not trust a small count from a wide page. Rule: census by ≤10 000-block windows and compare per-window counts (this session's: 124 vs 3497 vs 9109 `bEIGEN` Transfer logs per 60 000 blocks for recent vs V2-era windows, blocks 21.46M–21.52M and 20.94M–21.0M); a wide single page either 400s or silently under-answers.

14. **When the research lane's Alchemy budget is exhausted for the day, an ethereum `eth_getLogs` falls back to a public node that serves only short, recent windows — and the relay surfaces its 400 instead of retrying a provider.** Measured 2026-11-09 run f194c191 (research lane, `alchemy_cu_today.research` 502390/500000, head 26379179): the same address-filtered page that returned 36 logs at 26371179-26379178 answered `all providers failed: public: HTTP 400 {"error":{"message":"ranges over 10000 blocks are not supported on free plan","code":35}}` for a 10000-block page, the same error for an 8000-block page whose fromBlock sat 16000 blocks behind head, and succeeded (30 logs) for the identical 8000-block page 8000 behind head: the public node caps the *range* at 10000 blocks **and** answers logs only within roughly the last ~12000 blocks. Rule: while `/health` shows the lane's Alchemy budget spent, census with pages <=8000 blocks *and* fromBlock within the last ~12000 blocks; a `[]` or a 400 from that lane says nothing about older-window activity, and the error text ("all providers failed") is the budget signal, not a malformed filter. Confirm budget state with `GET $RPC_RELAY_URL/health` before concluding a census window is empty.

15. **A wide address-less `eth_getLogs` page on a busy topic on Arbitrum or OP Mainnet either dies with the 10 000-log `HTTP 400` or answers `[]` - it never answers a busy count - while a 1-block address-less page works.** Measured 2026-11-10 run ee7ded5f (research lane, arbitrum head 523081842, optimism head 159371608): a 30 000-block topic-only page with the `cast keccak` `Transfer` topic0 answered `all providers failed: alchemy: HTTP 400` (the >10 000 matching-log cap of item 13) on both chains, while the same 30 000-block window sent earlier with a hand-mistyped `Transfer` topic0 answered a silent `[]` (0 logs) on both chains, and `tools/relay-probe.py getlogs-topic-only --chain arbitrum` run seconds later answered `topic_only=4` with `address_filtered=2` for that block's busiest emitter on a 1-block page. Rule: on arbitrum/optimism a topic-only registry hunt (unknown emitter) needs small pages (a few thousand blocks) and a *cast-keccak* control on the *same* range - a wide `[]` from a mistyped topic0 says nothing, and a wide busy-topic page never returns its count. For a rare event, pin the emitter address and use address-filtered wide pages instead.

16. **On the new Elysium chain (99901) the providers refuse `trace_block`/`debug_*` with `HTTP 401` (measured once: `all providers failed: public: HTTP 401`), so `eth_getLogs` + `eth_call` are the whole trace surface there — and the same hand-typed topic0 zero of item 10 reproduced on it.** Measured 2026-11-11 run 8fbcce67 (head 4498906, block time 0.147-0.152 s): the first `Transfer` scans used a hand-typed tail `…b0b0434d5c64b142` (64 characters) and answered `[]` on five windows *including* the window 4462000-4465800 where a relay-log-scan of the same filter had returned 950 USDC logs the same morning; only after copying `topics[0]` from a real USDC log (`…f55a4df523b3ef`) did the same windows answer 7153 USDC Transfers per 20000 blocks. Rule unchanged and chain-agnostic: `cast keccak "Transfer(address,address,uint256)"` (or copy a receipt topic) before recording any zero, and on elysium probe `trace_block` once — a 401 is permanent, not a retryable relay fault.

17. **A syntactically valid 64-character topic0 can be refused as `invalid argument 0: hex string of odd length` on elysium (and as Base's Variadic rejection) while its neighbor topics work.** Measured 2026-11-11 run 32f5dd6e (elysium research lane, head 4516500): every `eth_getLogs` whose `topics` contains `0xffa7b8eab7da67f412cc9575ed43464468f9bfbae89d1675917346ca6d8fe3c92` fails with `{"code":-32602,"message":"invalid argument 0: hex string of odd length"}` (public path, `fromBlock:"latest"`) or with `all providers failed: alchemy: HTTP 400 -32600` (numbered-block path, i.e. Alchemy's own topic-length error) - in topic slot 0 or 1, with either of two addresses or address-less. The same window with the neighbor claim topic `0x803206...3477` or the canonical Transfer topic answers normally. Rule: when one topic digest of a pair from the same contract is rejected, do not conclude "no logs" from its failures - it is a serialization/quoting fault (see `inbox/meta/2026-11-11-elysium-getlogs-odd-topic.md`); re-derive the digest with `cast keccak "<Event(sig)>"` and compare byte-for-byte with a log's `topics[0]` before filing a relay bug. Same-run notes: on elysium `fromBlock`/`toBlock` tags must have an **even digit count** (`0x01`, not `0x1` - odd-length block tags are the provider's "hex string of odd length" case); and a *correct* Transfer-filtered page answered `0` logs in one minute while the no-topics scan of the same window returned 609 - the same filter returned 380-400+ logs minutes later, so a zero from a correct filter needs a same-window control before it is recorded.
