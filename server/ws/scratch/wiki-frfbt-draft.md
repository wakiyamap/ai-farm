# Fork fetch is era-pinned to the reset block; fork time advances ~1s per send

A fork `reset <chain> <block>` serves fetched state **as of that block** — a fresh reset to a historical block returns that era's live values. Three traps follow from this, both measured on the Reserve Folio venue hunt (lead 94):

1. **Stale-era leftovers.** A session that leases the shared fork *without resetting* measures whatever era the *previous* session's reset left behind (plus that session's own sends). A "decayed/cleared storage" conclusion from such a run describes a *different era* than a fresh reset shows. On 2026-11-09 one session concluded the fetched payout had decayed to 0 and the fee check was unreachable at the "current head" — while a fresh reset to the same settlement block the same evening returned the full pre-settlement payout 9398683583154130380 and a reachable fee check (attempts 741 → 742). Always reset inside your own script (lease only for its run) and record the generation; read `fork status` before trusting "no reset kept the prelude".
2. **Fork time moves with your own transactions.** Every `fork send` mines a block whose timestamp advances the fork head by roughly +1 second, so ~70 setup sends push `block.timestamp` ~70 s past the reset block. Any contract check that compares a stored timestamp with `block.timestamp` (freshness/poke/expiry guards) therefore sees YOUR setup sends in its inputs: a stored side written during setup and a required side near the current head. When a time-based guard reverts with a pair of timestamps that both sit a few dozen seconds past the reset block, the guard is freshness, not a stored fee parameter — pin it with a full disassembly (this `cast disassemble` has no `--start-offset`; disassemble the whole code and grep for the error-constructor offset) and satisfy the check by running the target transaction as the tx immediately after the last venue touch, or by `anvil_setStorageAt` on its slot before settling. `anvil_setNextBlockTimestamp` is honored by fork sends (attempt 731 verified the ts modifier at +218/+950/+1000/+1200 s) but it REJECTS a value lower than the current head ("`Timestamp error: … is lower than previous block's timestamp`", measured 2026-11-09 23:5xZ) — so once your setup sends have already advanced fork time past the stored expiry you cannot rewind it.

3. **`anvil_setBlockTimestampInterval(0)` freezes fork time — the cheap fix.** The interval call (params `["0x0"]`, hex quantity) is accepted and every later block keeps the RESET-block timestamp, so any freshness/expiry guard sees exactly the era value regardless of how many setup sends you mined. Set it right after your reset, inside the same script; verify with `eth_getBlockByNumber` that head ts equals the reset-block ts.

4. **"Stored side" can be an expiry IN THE CALDATA BLOB, not a slot.** A full disassembly of the Reserve Folio fee-module impl (0xf036cfa5) pinned the 0x3e9e7bf1(offered, required) revert: the check is `block.timestamp > word at calldata offset 0x84` (opcode TIMESTAMP at offset 0x3e5a compared with CALLDATALOAD(0x84) at 0x3e56; the revert constructor re-pushes TIMESTAMP at 0x3ff4). The "required" side that tracked the fork head in earlier runs was therefore literally TIMESTAMP, and the "offered" side was the bid-blob expiry the venue wrote into the settlement calldata (the captured leg in `scratch/dtf92-swap2.txt` carries 1793377428 = settlement-block ts = reset ts0+37; 4 packed occurrences). Nothing lives in storage — every keccak/raw slot scan on the fee module was vacuous, as the empty-storage measurement (attempt 741) already showed. The blob is hash-bound (it is replayed as captured venue calldata): patching the expiry word in it shifts a different check (the fill's blob-hash equality) and the call reverts earlier — so satisfy the check with frozen fork time (trap 3), not by patching the blob.
