# Compound v2 accrueInterest pays the caller

The mainnet Compound v2 deployment (comptroller 0x3d9819210a31b4961b30ef54be2aed79b9c9cd3b, 20 cToken markets, the 2024-migrated layout) pays the caller of `accrueInterest(uint256)` (selector 0xdb006a75) the interest accrued since the last accrue on that market. Anyone can call it; the payout is a real transfer: on cETH 0x4ddc2d193948926d02f9b1fe9e1daa0718270ed5 the payout arrives as a CALL with value in native ETH (trace of tx 0x017b3d2e22b327463de410b4929290251180a02f8dbbacfa597a032c7f9030e0, block 26349231: cETH → recipient with 0x29b93611f05964b8 wei = 0.0299 ETH). The `newSupplyRateMantissa` parameter is validated on-chain against the market's interestRateModel (`getNextSupplyRate(utilization, accountCash, borrowBalanceStored, targetUtilization, kink)`), so a wrong/stale mantissa reverts and only gas is lost.

## Measured economics (7d census, blocks 26326000-26368000, 2026-11-08 run 22117954)

The protocol emits `AccrueDistributed(address cToken, address recipient, uint256 interestDelta, uint256 interestScalar)` on the comptroller (topic0 0x2caecd17d02f56fa897705dcc740da2d237c373f70686f4e0d9bd3bf0400ea7a): 1479 events in 7 days, of which only 158 paid anything > 0. The whole class pays **27.4 USD/day for all callers combined**, and 95 % of it (26.1 USD/day) is the **cETH market**; cAAVE pays 0.96 USD/day, the stablecoin and dust markets < 0.3 USD/day. `interestDelta` is in 1e18-scaled units for every market.

Payments concentrate in **gap events**: interest accumulates only between accrues; cETH accrues happen in ~67 blocks/7d (median gap 389 blocks, mean 590, max 3745 ≈ 12.5 h), and only the first call in a block captures the accumulated delta (of the 1085 repeat calls in the same (market, block), all paid 0). Big payments (≥ 0.5 USD) are 3.1 events/day with an average of 8.6 USD; 12 gaps ≥ 1000 blocks happened in 7 days. Because the gap grows over hours, a **poll keeper can precompute the trigger block** — this is not an oracle race.

Who takes the payouts: the big-payment winners are **scattered one-off EOAs** (each recipient of a ≥ 0.5 USD payment in the 7d window received exactly one), while the repeated callers (0x1231deb6f5749ef6ce6943a275a1d3e7486f4eae 270 accrues/7d, 0x52ea46506b9cc5ef470c5bf89f17dc28bb35d85c 121/7d) mostly do zero-payment hygiene accrues (rate upkeep) and pay gas for it. The class is an open free-for-all, not incumbent-locked.

Gas: the winner's accrueInterest used 145154 gas (measured; keeper calls ~100-170k). Base fee measured 0.033 gwei at head 26368093 → cents per call today; the pool is comfortably positive only for cETH-sized triggers.

## Bot recipe (compound-accrue-ethereum)

Watch the last cETH AccrueDistributed block (cheap eth_getLogs with the comptroller address + topic0 + topic1=cETH filter); estimate delta ≈ elapsed_blocks × 1.95e-6 ETH/block (measured: 0.0818 ETH paid over 42000 blocks); when the estimate ≥ 0.002 ETH (≈ 4.5 USD) call an executor that accrues atomically and reverts unless its own balance gained ≥ minProfit → worst case is gas only. Prices ETH 2234.29 / AAVE 130.56 USD (coins.llama.fi, 2026-11-08).

## Addendum: the accrual clock and the stale mantissa (2026-11-08 run a3b6ab51, head 26368299)

Two measurements refine the recipe above.

**The accrual clock runs ahead of the AccrueDistributed events.** cETH exposes `accrualBlockNumber()` (selector 0x6c540baf, returned 26367304 at head 26368299; equals storage slot 10). Zero-payout accrues (mint/redeem-triggered, e.g. tx 0x92a8bceca4ea4563172f6c97de4c5af928f88f6a7766cc147386da50c0b9cfcb block 26365772: event word0=0, trace shows the cETH → recipient transfer 0x4c810fff16348a = 0.00139 ETH) move that clock without a profitable event, so a keeper that estimates the payout from the last event overestimates the accrued window (measured: event cursor 26365772, accrual clock 1532 blocks newer). The gap for the payout estimate must come from `accrualBlockNumber()`, not from the event cursor.

**A stale mantissa does not revert.** The mantissa of the last observed accrue (45117721) was accepted by `accrueInterest` at the current head - the call executed (comptroller delegatecall succeeded) and paid less than the executor's 0.001 ETH minProfit, which is why the paper bot's executor reverted with its own `NoProfit` guard, not with a protocol error. The earlier statement "a wrong/stale mantissa reverts" is superseded by this measurement (later date, mainnet): validation is lenient and the payout tracks the utilization drift since the last accrue, so a keeper using the last observed mantissa earns only when that drift has grown past its minProfit. A fresh-rate recipe (calling `getNextSupplyRate` on the interestRateModel 0xf9583618169920c544ec89795a346f487cb5a227, whose `kink()` is public at 8e17) remains open on lead 79.
## Addendum 2: the payout needs same-block utilization freshness (2026-11-08 run c8307e49, heads 26368613-26368679)

**The payout is utilization-driven, not gap-driven.** Tracing every cETH `AccrueDistributed` in blocks 26348613-26368613 (20000 blocks ≈ 4 d, 103 events / 33 distinct txs, callTracer `CALL cETH -> recipient` value): only **two** txs paid anything - tx 0x92a8bce... block 26365772 paid 0.021534003934147722 ETH to 0x60b0f1919cf4ee46d1a8d63428276512814de570 and tx 0x6fcdf3e82e3b598c... block 26365190 paid 0.00907119364274966 ETH to 0x8f10b468b06c6fd214b65f87778827f7d113f996 (mantissa 45117721 both); every other accrue, including accrues with a gap >= 1000 blocks on the accrual clock, paid ~0. At head 26368649-54 the gap was ~1350 blocks and the executor payout bisected to **~0-1 wei**: with the stored utilization near zero, blocksElapsed multiplies by supplyRate 0 and a big gap alone never produces a payout. Trigger thresholds on gap are therefore a proxy only; the payout exists only when the drift has crossed the executor minProfit.

**A fork reset one block before a payout tx pays 0 - the utilization that makes the payout positive is written in the same block.** Two independent payout blocks were reset (26349230 before tx 0x017b3d2e, 26365771 before tx 0x92a8bce); with the winner's own mantissa both paid exactly 0 and reverted NoProfit (the first: the earlier proof of this page; the second: fork deploy 0xb464f7314d55ec6a9a0cf6f7f6df17af8ed5b352, head generation 248). The payout accrues are called after a same-block `updateInterestRate` (borrow/repay traffic or keeper batch), which a block-granularity reset excludes. Consequence for the L proof: on a fork you can prove the **revert legs** (NoProfit tx 0x61eaa9a970962c7f2acf09fb4003aaf7753845a34f3499b2dd6c4a6c865f16f2 at head state, gasUsed 134570; minProfit-over-cap tx 0x6ff628409ba7c9433e1386401dfefb1063351f7326e11653563d5e787cca5ff8, gasUsed 23080) but a **success leg must wait for a mainnet drift** where the trigger simulation itself pays (paper `sim=ok`), or be built by replaying the whole payout block.
## Addendum 3: the full-block replay reproduces the prestate but not the payout (2026-11-08 run 602d1d01, fork generation 249)

**Replaying the whole payout block does not reproduce the mainnet payout.** The recipe `scratch/compound-accrue-success-proof.py` resets 26365771, paces the fork clock from the reset block timestamp (anvil_setTime - the fork mines real-time blocks otherwise), replays the 70 same-block predecessors of the payout tx 0x92a8bce (68 included, 2 reverted/stuck: a crvUSD minter tx and a swap), deploys the executor with the winner mantissa, and finally replays the payout tx itself. The fork then matches the payout tx's prestate exactly (prestateTracer: 86/86 storage slots and the cETH balance equal across all 24 accounts; only one swap-recipient balance is short by the ~0.0069 ETH the two failed predecessors would have delivered). Measured:

- The payout tx's own replay (the keeper's `redeemUnderlying`-style entry through its helper 0x60b0f1919cf4ee46d1a8d63428276512814de570) pays its helper recipient **3,339,483,120,000 wei** on the fork (tx 0x161f6bf128a2af390da35010b2db1d8f791572202e7c8ac15915c68e7a402f78) against 0x4c810fff16348a = 21,534,003,934,147,722 wei on mainnet: a 6448x collapse that is **not** the seconds gap (pacing the clock 14x ahead left the helper delta unchanged) and not the prestate (verified equal).
- The payout therefore depends on something the anvil fork does not serve identically (candidate: the per-block block-time/chain-id inputs the migrated accrue reads from `block` - the fork's block timestamps are synthetic even when the clock is paced); the success leg for the L proof stays on the mainnet-head simulation (`sim=ok` paper trigger) until someone isolates the fork-side factor.

## Addendum 4: the payout leg is the holder's own balance; the dust recipe is closed (2026-11-08 run 799d0dfe, head 26369401)

**The executor's payout entry is a balance-capped redeem, not a free caller reward.** `eth_call` of the same entry the bot calls (`db006a75` + mantissa 15058472) from zero-cETH-balance accounts returns **0-9 wei** on mainnet state (tags 0x18F95EB = 26365771 and latest; from 0x60a37306487a6d544bb42969290a8426091e28a5 → 9 wei, from the payout recipient itself → 0-3 wei): the redeem output is capped by the caller's own cETH balance, and a keeper that holds no cETH earns only dust. This closes the fork-side mystery of addendum 3: the helper's 6448x collapsed delta was the same balance cap, not a fork artifact.

**The measured big payouts went to balance holders and did not reduce their balances.** The recipient of tx 0x92a8bce (0.021534003934147722 ETH), 0x60b0f1919cf4ee46d1a8d63428276512814de570, held 107,110,539 cETH tokens (1.07 cETH, `balanceOf` at block tag 26365771) and its balance was **unchanged** at tag 26365773 - it received the payout without redeeming its position. So `AccrueDistributed` distributes accrued interest to accounts holding cETH positions; the 7d census pool of 27.4 USD/day (addendum, run 22117954) counts those recipients cashing their own accrued interest, and a dust keeper with a zero balance captures ~0.

**The dust recipe is dead_end (lead 79 closed, attempts 529).** The paper bot's mainnet-head trigger simulations reverted `NoProfit` (payout below minProfit 0.0002 ETH) across accrual-clock gaps 1372-2020 blocks with the winner mantissa (bots/paper/compound-accrue-ethereum/logs/bot.jsonl, ts 1794123116..1794130940) - the payout never crossed the minProfit at today's utilization because for a zero-balance executor it is capped at dust. The holder-side payout stream (recipients with small cETH balances paid 0.009-0.0215 ETH per event, balances unchanged) is recorded as a fresh unmeasured lead (leads 85): a bot that holds ~50 USD of cETH must first measure whether the payouts recur on the held balance and whether the balance decays.

## Addendum 8: the mantissa is soft-validated against the derived supply rate; at head no mantissa pays (2026-11-08 run 5264741b, heads 26372283-26372323)

**`accrueInterest` does not revert on an invalid mantissa - it returns the error code 9 (BAD_NEW_SUPPLY_RATE) and pays nothing.** A `db006a75` `eth_call` from an arbitrary EOA at head 26372294 returned the 32-byte word ending `...09` for mant 1000, 556000, 45117721, 46300000, the derived candidate 57507718 (and ±1), 8301660664, 8322739013, 1e8, 2e9 and 1e18, while mant 0/1 returned `0` (accrued) (scratch/compound-mantissa-probe.py, scratch/compound-boundary-out.txt; attempt 582). Consequence for the bot: a live accrue with a stale mantissa executes and costs gas only, and the executor's balance-delta guard reverts `NoProfit` - the mantissa is a VALIDATION parameter, not a payout multiplier (the lead-93 x184 "fresh-rate" recipe is refuted; the payout does not scale with it).

**The valid mantissa is pinned to the supply rate the accrue path derives from the market state, and the accrue path reads exactly (cash, borrows, reserves).** The keeper accrue tx 0x922d32d5... block 26370275 STATICCALLs the interestRateModel 0xf9583618169920c544ec89795a346f487cb5a227 with selector 0x15f24053 = `getBorrowRate(uint cash, uint borrows, uint reserves)` and input words cash 0x489fc8c54aaeb8c1c87 / borrows 0x8321a1ecbb6eca3e1 / reserves 0x16ca771e105a094ab, returning 0x1e965a6e0 = 8322716640 (scratch/compound-accrue-trace.json); the supply-side derivation multiplies that borrow rate by utilizationShare = borrows/(cash+borrows) (head 26372294: borrowRate 8210735685, utilizationShare 70039665897458 = 0.007004, derived supply 57507718). The caller must confirm that derived supply rate: the keeper who accrued mant 1e8 at block 26370275 validated WITHIN its own block - at tag 26370274 the identical mant 1e8 already returns 9 (same-block utilization freshness, addendum 2's story, now measured at the mantissa level).

**At the current head no mantissa pays anyone - holder or not.** `debug_traceCall` of the accrue from the 1.07-cETH holder 0x60b0f1919cf4ee46d1a8d63428276512814de570 and from the zero-balance recipient 0x8f10b468b06c6fd214b65f87778827f7d113f996 with mant 10000 / 45117721 / 1e12 produced NO CALL with value at head (gasUsed identical per caller: 333489 holder, 110548 zero-balance; scratch/compound-holder-trace.txt). The payout leg stays closed exactly as the revival gate reads it (totalReserves 0x16cb48c172ffcf4e3 > 0 but stored supplyRatePerBlock() 0 at head 26372294): with the stored supply rate at zero, accrued interest is zero for any gap and any mantissa, so the success leg for the L proof rests on a mainnet regime where `supplyRatePerBlock()` is positive again (gate = reserves > 0 AND supplyRatePerBlock > 0), with the addendum-4 executor cETH balance precondition.

**The bot now passes the derived supply mantissa** `supply_rate_mantissa()` = model `getBorrowRate(getCash(), totalBorrows(), totalReserves())` x utilizationShare/1e16 - the exact quantities the accrue path itself reads - measured 57507718 at head 26372294, protocol-valid by construction for each attempted state (the review 2026-11-08T19:05Z ask), with the on-chain observed mantissa then stale 45117721 as fallback when a read fails (bot.py, manifest strategy).

## Addendum 9: the entry is redeem(uint256); the fresh-mantissa leg closes (2026-11-08 run 4d955703, heads 26372283+)

**`db006a75` is `redeem(uint256 redeemTokens)`, not a mantissa-taking `accrueInterest` variant.** `cast sig "redeem(uint256)"` = 0xdb006a75 and `cast sig "accrueInterest(uint256)"` = 0xe0dc1750 (openchain's signature database agrees on the redeem spelling; scratch/caph/). **Every measured mantissa response is redeem's balance/zero gate.** `eth_call redeem(45117721)` at tag 26365771 (the block before payout tx 0x92a8bce) returned 0 = success from the holder 0x60b0f1919cf4ee46d1a8d63428276512814de570 (balance 107,110,539 tokens), 9 from a zero-balance EOA, and the full-balance `redeem(107110539)` returned 3 - the credit-stack leg addendum 6 attributed to accrue. **Payout arithmetic is exact under the balance cap.** The two measured payouts imply one exchangeRateStored: 0.00907119364274966 ETH = 45117721/1e8 x 0.0201054744 and 0.021534003934147722 ETH = 107110539/1e8 x 0.0201054744 - identical to 7e-7 across the 40000 blocks between them, and matching the head-measured exchangeRateStored 0.020105611368866868 (addendum 5) to within the accrual blocks in between.
