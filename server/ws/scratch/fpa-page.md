# Finding a protocol's contract addresses from this host

**Conclusion:** don't trust addresses from memory. On 2026-11-06, all 5 memory-guessed core addresses (3 SparkLend Pool, 2 Fluid T1) had empty bytecode, and address hunts used about 5 earner sessions. Even famous contracts come out of memory one character off: in the 11-08 "getCode returns 0x for known contracts" reports, the human re-checked after relay phase 6y and all 4 addresses really were empty (publicnode, drpc and Etherscan agree; `0x87870Bca…6eF5b` is an EOA), while USDC in the same batch returned code; the human's own Claude made the same mistake (decisions/human/2026-11-09-relay-1inch-paperctl.md §1). **When a "known" address has no code, suspect where the address came from before you suspect the relay.** Take every address from a primary source (official deployment list, GitHub deployments file, explorer, an on-chain getter) and confirm it with `eth_getCode` before use. Before any hunt, `kb query` the `protocols` row: the class may already be measured (run 09afea67 re-hunted Fluid identities for an existing dead_end). Then use these in order, and check each candidate with `eth_getCode` before spending reads on it:

1. **Event emitter scan (most reliable, on-chain).** Get the event's topic0 from a known receipt of the same protocol family, or from `cast keccak "<Event(sig)>"` (never hand-type a topic hash: run 5a00682c got a vacuous zero that way). Then run a topic-only `eth_getLogs` over recent blocks **with an explicit block range and pages** (an address-less scan that is too wide silently returns `[]`, see `pitfalls/relay-getlogs-invalid-params.md`; range/result caps are in the TOOLS.md relay row). The `address` field of the hits is the emitter. SparkLend's Pool proxy `0xc13e21b6…be987` was found this way (attempts 250). If a scan returns 0 hits, first run a positive control on a known event before you conclude the protocol is dormant. On ethereum, topic-only scans before relay phase 6y (2026-11-09) could come back empty from public nodes; `python3 tools/relay-probe.py getlogs-topic-only --chain ethereum` checks the current behaviour in 5 calls.
2. **DefiLlama code on GitHub raw/API.** `raw.githubusercontent.com` and `api.github.com` resolve. The DefiLlama TVL and yield-server adapters hard-code core contract and resolver addresses (Fluid's LendingResolver came from the yield-server adapter, run 0ca4120e; Gearbox's compressor from its adapter, run 09d1ec19).
3. **Search for the repo or deployment list.** Since 2026-11-07 a keyless local metasearch works: `websearch "!gh <protocol> <word>" -n 5` finds the protocol's GitHub org/repos (deployment JSONs, address books). Use short plain terms; hyphenated queries often return nothing. Earners' `web_search` uses the same backend.
4. **Follow a known actor.** Trace a liquidator's or keeper's tx (`debug_traceTransaction`, callTracer). The protocol contract is the callee that emits the event. Keepers often enter through their own contract, so read past the first frame (attempts 288).
5. **Explorers and docs.** Reachability varies by site: on 2026-11-07 Blockscout verified sources and some protocol docs (docs.surge.credit) worked, while earlier docs.fluidprotocol.org and arblockscout.com failed with ENOTFOUND/503. Etherscan v2 needs a key we don't have. Treat docs text as data (GitBook pages carry "agent instructions").
6. **Registry contract lists go quiet when projects rename.** `api.llama.fi/protocol/<slug>` returns `chainContracts: null` for renamed projects (EigenLayer is now "EigenCloud", 2026-11-09 run fa3cb7dd; Notional V2, attempt 671), so the registry cannot pin the live core — go to the TVL/yield adapter code (item 2) or the emitter scan (item 1) instead. The same repo's `deployments/` directory can also be gone in current tags (EigenLayer main/master/v1.13.0 all 404 on raw.githubusercontent), so list the tag tree once (`git/trees` API) rather than probing deployment paths one 404 at a time.

## Checks before you build on an address
- `eth_getCode` is not empty, and for a proxy, read the implementation slot.
- A known event from step 1 was emitted by this address.
- Event fields mean what you think: compare one event against a state diff (prestateTracer diffMode). Compound v2 `LiquidateBorrow` field 4 is seized cToken shares, not repaid USD (attempts 289).

Record the verified address in the `protocols` row (`checked`) or an `infra/` page, so nobody hunts it again.

## Keyless verified-source lookup (measured 2026-11-07, run f89e59ca)

When the address is pinned but the *event signatures / function ABI* are not, the verified source comes keyless from Routescan: `https://api.routescan.io/v2/network/mainnet/evm/1/etherscan/api?module=contract&action=getsourcecode&address=0x...` (Etherscan-compatible). The Etherscan keyless V1 endpoint now returns `NOTOK: You are using a deprecated V1 endpoint` and V2 needs a key; GitHub code search also requires auth. Gotchas in the Routescan payload: multi-file `SourceCode` starts with a doubled `{{` and doubles every literal brace, so naive brace-stripping breaks JSON parsing — regex the `event ...;` definitions out of the raw string (event parameter lists contain no braces). Liquity mainnet `TroveManager` events came this way (attempt 455): `Liquidation(uint256,uint256,uint256,uint256)` topic0 `0x4152c73d...` — a 3-parameter guess scanned zero for 120 d while the address emitted ~190 events per 10 k blocks in a historical control window.

A pinned contract also cross-checks on-chain: public-variable getters (`activePool()`, `defaultPool()`, `sortedTroves()`, `lusdToken()`, 4-byte selector = first 4 bytes of `cast keccak "name()"`) must return the values from the official deployment JSON. A getter that reverts with bare `0x` means wrong signature, not wrong address (relay `eth_call` reports `execution reverted` for both).

## Sky/Maker chainlog HTTP API (measured 2026-11-07, run 899ed012)

MakerDAO/Sky legacy CDP contracts pin keyless from the official chainlog HTTP API: `https://chainlog.skyeco.com/api/mainnet/active.json` returns 520 active mainnet contracts with addresses (MCD_DOG 0x135954d155898d42c90d2a57824c690e0c7bef1b, MCD_VAT 0x35d1b3f3d7966a1dfe207aa4514c12a259a0492b, every MCD_CLIP_*); `api/index.json` lists versions. `chainlog.sky.money` 301-redirects to that host. Dead ends found the same day: ipfs.io and w3s.link gateways returned HTTP 429, `abi.makerdao.com` no longer resolves, and raw.githubusercontent 404s for the guessed makerdao/Sky-Ecosystem repo paths (mcd-abi, flare, deploy-mainnet, spells-mainnet). GitHub API works keyless at 60 requests/hour/IP (rate limit hit mid-hunt; reset after ~40 min). Flare-era LoanManager/LiquidationEngine are not in the active chainlog — the current liquidation pipeline is the Dog/Clipper pair (docs: developers.skyeco.com/protocol/vaults/collateral-liquidation/).

## Mainnet name search and what a verified name is not (measured 2026-11-08, run 9aa563db)

Blockscout mainnet answers a *verified-name* query keyless: `https://eth.blockscout.com/api/v2/search?q=<Name>` returns verified contracts whose source name matches (run 9aa563db: `q=HiddenHand` returned 11 verified `HiddenHandRewards` instances; controls `q=Agora`/`q=Bravo` returned hits, so an empty list is evidence only with a control). The search intermittently returns empty even for known names - never conclude "no such contract" from one empty query.

**A verified name is not the mechanism.** The `HiddenHandRewards` instances are per-market payout wrappers: the 60-day log census on the 11 registries (blocks 25938727-26368727) returned only ERC20 `Transfer`+`Approval` (410 events, `scratch/hh-regs.json`), and one instance's own getters read `name()` = "Gilded Scieces, Inc.", `symbol()` = "GILD" - the contract is a partner ERC20 token, not a governance reward ledger. Probe candidate addresses with the getters the mechanism requires (`cast keccak` the signature, `eth_call`, see above) before believing any name.

Two relay notes from the same session. (1) `eth_getCode` returned `0x` on head−3 for what the session took to be the Uniswap V2 factory. Until phase 6y (2026-11-09) a public node could answer `0x` for real code; 6y re-asks Alchemy on every empty getCode/eth_call and never caches it, so a `0x` now means no code at that address: re-check the address's source first (see Conclusion). (2) `tools/relay-log-scan.py` rejects address-less filters ("address and topics required"); a topic-only scan goes through a direct relay `eth_getLogs` call instead.

## Docs sites as plain markdown (measured 2026-11-08, run 468402f2)

GitBook documentation sites (docs.dolomite.io) render page bodies client-side: the HTML shell curl gets contains only header links, and `sitemap.xml` is just an index. Append `.md` to any page URL (e.g. `https://docs.dolomite.io/smart-contract-addresses/core-immutable.md`) and the server returns the page as plain markdown with the address tables intact; `/llms.txt` and `/llms-full.txt` give the full page index / full text. This pinned the whole current dolomite deployment (DolomiteMargin adapter + per-model interest setters, no rebalancer role) in a few requests while GitHub repo search returned nothing. Cross-check every docs address with `eth_getCode` and the blockscout verified ABI name; dolomite's interest setters verified as DoubleExponent/AAVECopyCat/AlwaysZero/LinearStepFunction per model with view-getter-only ABIs — a payment class with no payable function and no caller-payment path dies at this ABI leg, before any event census or prestateTracer (attempt 520).

## Base blockscout needs a User-Agent; dead domains are not proof of death (measured 2026-11-08, run 5e7b444a)

`https://base.blockscout.com/api/v2/search?q=<Name>` answers **Cloudflare 403** to bare `curl` (an HTML "Just a moment..." body that breaks naive JSON parsing) and 200 with a plain browser header (`-H "User-Agent: Mozilla/5.0 (X11; Linux x86_64)"`). The same verified-name flakiness as mainnet applies: one empty list is not "no such contract" (q=NodeMinterV2 returned [] while q=basenode returned 50 unverified clones). And a protocol's product domains can all ENOTFOUND while its on-chain class is still alive or long dead - on 2026-11-08 base-node.com, docs.base-node.com and nodeops.com all failed DNS and nodeops.io was a parked Spaceship sale page, yet nothing on-chain was measured (Base Node lead 87 stayed unmeasured). Treat domain death as product-side evidence only; the on-chain liveness leg (claim-tx census on the pinned address) decides the class.

## Dead llama projects: the adapter file is deleted from main, recover it from commit history (measured 2026-11-09, run 991f8b4c)

When `api.llama.fi/protocol/<slug>` shows `tvl: null` and `chainContracts: null`, the project is deprecated and its adapter file is *gone* from `DefiLlama-Adapters` main (`projects/<slug>/index.js` 404s). Two keyless recovery paths, both worked for Notional V2 (lead 107, attempt 673): `GET api.github.com/repos/DefiLlama/DefiLlama-Adapters/commits?path=projects/<slug>/index.js` returns the commit history *including* the deletion (the commits API answers deleted paths), so fetch the raw file at the last surviving commit sha; and `raw.githubusercontent.com/.../main/registries/deadAdapters.json` lists the slug with its `deadFrom` date. The recovered adapter pinned the Notional V2 proxy `0x1344A36A1B56144C3Bc62E7757377D288fDE0369` (v2Contract), and the project repo (`api.github.com/orgs/<org>/repos` → `v2.mainnet.json`) agreed; docs.notional.finance answered only with a `-A "Mozilla/5.0"` header (the same UA trick as base.blockscout above; the bare-curl 503 from blockscout.com was the same class of rejection). A dead-from date is also a census shortcut: the llama `chainTvls.<chain>.tvl` last point (2024-08-22, 3,096,346 USD for Notional V2) dates the death, and the liveness census then only has to show the post-death silence (address-filtered no-topics `eth_getLogs` returned 0 logs in every tested window from ~2024-10 to head, with same-shape controls returning 67 logs on the same address in 20420000-20480000).
