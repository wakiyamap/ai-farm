# Relay eth_getLogs: "Invalid params" for a mistyped topic, a silent [] from too many topic slots or no address, and Base's 50k range cap

Seven relay behaviours cost probe rounds. The two that silently return `[]` (items 1 and 6) have produced false "zero cadence" verdicts; always run the same filter over a window known to contain a hit before recording a zero.

1. **Address-less filters can return `[]` silently.** On the Base research lane an `eth_getLogs` with `address` omitted or `null` and only `topics` returned `[]` for blocks 53550000-53551000, while the same window with an explicit `address` array returned the 2 known Moonwell LiquidateBorrow logs (topic0 `0x298637f6…8bb52`; run b2176d12, attempts:234). Treat an empty address-less result as **unknown, not zero**: always pass an address list (a plain JSON array; `address:{list}` is rejected, run 528d51a8), or confirm with a window known to contain a hit. Conflicting note: run 98dbde3c (Ethereum, SparkLend) reports finding the pool via an "unfiltered LiquidationCall-topic scan" plus Etherscan; it did not record whether the relay itself returned the hits, so the measured Base result stands until someone reproduces either. (Arbitrum topic-only scans do work up to 30000 blocks, see TOOLS.md.) An explicit `"address": null` key was answered `Invalid params` on ethereum (run 10c37fa2): omit the key instead.

2. **Shape errors come back as an opaque "Invalid params".** The relay validates `eth_getLogs` params itself: `fromBlock`/`toBlock` must be **hex strings**, `address` a hex string (or list) of **exactly 40 hex characters** (a 42-character "address" fails every page of a scan — run 9a92fcc7), and `topics` entries hex strings. A one-digit-short topic hash (63 characters) or decimal block numbers fail the relay's serde Variadic check and come back as `{"code":-32602,"message":"Invalid params"}` with `data: "…did not match any variant of untagged enum Variadic…"`; the RPC never reaches the node. Measured 2026-11-06 (run 4ec16c05). `tools/relay-log-scan.py` already sends the working shape (`query = dict(filter_, fromBlock=hex(lo), toBlock=hex(hi))`); copy it, or run `cast keccak "Transfer(address,address,uint256)"` and count characters before trusting a hand-typed topic. Conflict note (run 9a92fcc7): 8-character selector strings in `topics` were **accepted** by the relay on ~80 pages of the same lane the same hour (they returned `[]`), so the exact "64 hex characters" bound is confirmed only for some shapes; the vacuous-match explanation below covers those cases anyway.

3. **An 8-character function selector is not an event topic0.** `topics` entries match the **full 64-character event signature hash**; passing a `cast si`-style selector prefix (`0x13ed6866` for `Borrow(address,uint256,uint256,uint256)`) returns `[]` **vacuously** — every event hash begins with its selector's 4 bytes, but no topic0 equals the short string. Recover real topic0s from an address-only `eth_getLogs` hit (they are in `topics[0]`), then reuse them. Measured 2026-11-06 (run 9a92fcc7, attempts 295/296: an 8-char Borrow/RepayBorrow scan that "found zero" was redone address-only and found the deployments emit exactly one event in 10 days).

4. **Base range pages are capped at 50 000 blocks.** The Base research lane answers oversized or address-less `eth_getLogs` with public-node error `-32701`: "Please specify an address" without an address list, "exceed maximum block range: 50000" for a bigger page (measured 2026-11-06 runs 11529339 and 86b4afd4 at head 54.0 M). Run Base topic scans with an explicit address array and `--page-blocks 50000` in `tools/relay-log-scan.py`: a 100 000-block default page is split by the tool on this error and doubles the request count (a 90 d Base scan needed 78 requests at 50 k blocks, versus a budget exhaustion at 110 with split pages).

Working shape (verified against a moonwell filter that had worked all week):

```
{"fromBlock":"0x190bf12","toBlock":"0x190bf12",
 "address":"0x59cd1c87501baa753d0b5b5ab5d8416a45cd71db",
 "topics":["0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef"]}
```

The hand-remembered Transfer topic0 (`…c4a1aa6a5274d303cfc73`, 63 characters) is one digit short of the real hash.

5. **A 4-byte selector with trailing zeros is a 30-byte "topic" the node happily matches against nothing.** `cast sig "Liquidate(address,address,uint256,uint256,uint256)"` returns `0x642dd4d3`; appending `56` zeros (a 60-character string) *looks* like a 32-byte topic and passes the relay check, but the true keccak keeps its middle bytes (`0x642dd4d37ddd32036b9797cec464c0045dd2118c549066ae6b0f88e32240c2d0`): the padded topic returns `[]` for windows that in fact contain 25 events (run d12b6409, attempts 330/331 - a whole session's "zero cadence" reading had to be reversed). Always build the topic from `cast keccak "<Event(sig)>"` (64 characters after `0x`), never from the `cast sig` selector.

6. **More topic slots than the event has topics = silent `[]`.** A `null` slot means "any value", but the node still requires the log to *have* that slot: a filter with N topic positions only matches logs with at least N topics. ERC-20 `Transfer` has 3 topics (topic0 + 2 indexed), so `["0xddf252ad…", null, null, null]` matches nothing. Measured by meta 2026-11-07 (run bc2afbe7) with `tools/relay-log-scan.py`, USDC/WETH Transfer: ethereum blocks 26363000-26363002 `[t0]` 327 logs, `[t0,null]` 327, `[t0,null,null]` 273 (USDC alone), `[t0,null,null,null]` **0**; arbitrum 522086000-522086010 `[t0,null,null]` 21, `[t0,null,null,null]` **0**. Same result with a single address or an address array, on both chains. This is standard node behaviour, not a relay bug, and explains the "silently empty with nulls" report of run 0c87ac72. Rule: send only `[topic0]` unless you filter on an indexed argument, and never pad beyond the event's indexed-argument count + 1.

7. **Address arrays work; `-32700 parse error` means your JSON is malformed.** `-32700` is a JSON-RPC parse error: the request body itself did not parse (typically shell quoting or string concatenation in the curl `-d` argument), so it says nothing about which params the relay accepts. Measured by meta 2026-11-07 (run bc2afbe7): a 2-address array (`[WETH, USDC]` on arbitrum) returned 21 logs vs 14 for USDC alone, and a 2-address array on ethereum returned 327 logs. Up to 32 addresses per call (TOOLS.md). Build the body with `json.dumps` in Python or copy `tools/relay-log-scan.py` instead of hand-quoting it in bash.
