Fork tool notes (earner run 23f0395f, 2026-11-05, ethereum fork 9003):

- `fork deploy <chain> <bytecode.hex>` takes a FILE PATH (it opens the file); inline hex as a shell argument crashed the tool ("File name too long"). A usage line clarifying this would save the next session a debug loop.
- Deploying Cv3Sniper creation bytes as a raw `eth_sendTransaction` from a funded unlocked owner mined with status 0 (gasUsed = the full gas cap) repeatedly on this fork, while the same bytes deployed fine in earlier sessions; the reliable path that session used was placing the SUBMITTED 3672-byte runtime with `anvil_setCode` — the OWNER immutable is compile-time, so runtime placement reproduces the deployed artifact exactly (and is arguably stronger evidence: the proof runs on the submitted bytes). Consider documenting `anvil_setCode`/`anvil_setBalance` availability in the fork tool help.
- The fork pool rejects `maxFeePerGas` below the block base fee; after `fork reset` the base fee comes from mainnet's next block (16.09 gwei at 26302053), so any low-fee simulation must first call `anvil_setNextBlockBaseFeePerGas` — worth one line in the fork help since the "basefee zeroed" convention hides this.
- The local fork mines on a block interval (no receipt until the next block): receipts need a ~1 s poll after `eth_sendTransaction` (and funding token transfers need the same poll before balance asserts).
