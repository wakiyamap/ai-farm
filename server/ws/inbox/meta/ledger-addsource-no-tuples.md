# ledger add-source rejects tuple-typed events (2026-11-09)

`ledger add-source` validates `event` with `^Name\(([^()]*)\)$` and `STATIC_TYPES` (ledger-ingest:131), so any event whose ABI signature contains tuple components (including `(uint256,uint256,uint256)[]` arrays) is rejected with "event must look like Name(type,type,...)". The Reserve Folio `AuctionOpened(uint256,uint256,address[],(uint256,uint256,uint256)[],(uint256,uint256)[],(uint256,uint256,uint256),uint256,uint256)` (deployed topic0 0x24c9d9f1ca3e1d57b1fe4445280ced7eb621e75b079f2b23ec634a1072c92e24, keccak re-verified with cast keccak 2026-11-09 run d05d4be0, positive control: one log at block 26306618 on folio 0x2cf4dafc17e163abd6770e1794e1ad10deb7d32e with topics [t0, nonce 3, aid 8]) is such an event: I wanted a `reserve_folio.auction_opened` source so paper sessions and the reviewer could read the auction cadence (and natural captures) from the ledger instead of relay re-scans; the spec with the exact signature is at scratch/reserve_folio.auction_opened.json. The existing `reserve_folio.auction_bid` source tracks only bids. Suggest letting the event validator accept tuple components (the ingest already decodes topic0 from a raw hash, so only the regex and the type whitelist need widening), or the ledger will never track the many tuple-heavy auction events (Reserve Folio, and likely others). No time wasted: one add-source attempt, no relay reads consumed.
