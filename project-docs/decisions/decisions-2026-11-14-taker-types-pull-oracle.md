# 取り手の型を tx から見分ける。Pull 型オラクルの市場を調べる（人間、2026-11-14）

同じブロックで清算を取る相手が、どうやって検知しているのかを整理しました。型によって、farm が真似できるものと、できないものがはっきり分かれます。これまでの測定は「何秒で取られたか」だけでしたが、これからは **「どの型で取られたか」も一緒に書いてください**。速い相手でも、型によっては farm が同じ土俵に立てます。

decision 2026-11-13-follow-slow-liquidators、2026-11-13-liquidator-clusters、2026-11-14-copy-other-bots、2026-11-14-race-rule-seconds、2026-11-14-crash-postmortem-rival-contracts はそのままです。ここで足すのは次の 3 つです。

## 1. 取り手の型（earner が測るときに付ける）

清算の事例を測るとき（census の秒数の測定、急落の事後検証の 1-2、相手のコントラクトの解析の 2-3）、1 件ごとに次のどれかを付けます。根拠は tx hash で示し、判断できなければ「不明」と書きます。推測で埋めないでください。

- **P（Pull 型）**: 清算の tx の中で、取り手自身がオラクルの価格を更新している（Pyth の価格更新の呼び出し、RedStone のように calldata に署名つきの価格を付ける形など）。価格更新と清算が 1 つの tx なので、きっかけはオンチェーンのイベントではなく、オフチェーンの価格配信です
- **B（バックラン）**: 清算の tx が、同じブロックの中で、オラクルの価格更新の tx のすぐ後ろにある（目安: 間に挟まる tx が 2 件以内）。価格更新の tx の hash と、ブロック内の位置（両方の tx index）を書く。`block.coinbase` への送金があればそれも書く
- **O（オークション）**: 価格更新そのものが、清算の権利を売る仕組み（Chainlink SVR、Atlas など）を通っている。その市場のフィードが Standard か SVR かを、一次情報で確かめて書く
- **S（撃ちっぱなし）**: 同じ送信元が、同じ市場に向けて、失敗した tx や何もせずに終わった tx を繰り返し出している。測った期間の成功と空振りの件数、空振り 1 回のガス代（USD）を書く
- **T（時刻で決まる）**: 取れる状態になったきっかけが価格更新ではない（利息の積み上がり、満期、オークションの開始時刻など）。きっかけの時刻が前もって計算できたかを書く
- **不明**

運用者のカード（`infra/bot-census/<operator>.md`）には、その運用者の事例が型ごとに何件あったかを 1 行で足してください。

### 1-1. 型ごとの扱い

- **B と O は D（模倣できない）**のままです。farm は mempool の監視、バンドル、ビルダーへの直接送信、清算の権利の入札をしません
- **P は「速いから対象外」で終わらせない**でください。2 で調べます
- **S** は、空振り 1 回の費用と成功 1 回の差し引きから、1 日の差し引き（期間つき）を出してください。farm が同じことをする場合の費用（L、ガス代、Alchemy の CU）も並べます。作るかどうかは人間が決めます
- **T** は、きっかけの時刻が前もって計算できるなら、race-rule-seconds の区分をその時刻から数えてください。「数える」に入る事例があれば lead です（lead 44 と同じ扱い）

## 2. Pull 型オラクルの市場を調べる（researcher）

farm の 9 チェーンで、**Pull 型のオラクルで清算の価格を決めている貸付プロトコル**を一覧にしてください。1 プロトコル × チェーンで 1 行、wiki `infra/pull-oracle-markets.md` に置きます。数字には出どころを付け、分からない項目は「未確認」と書きます。

- プロトコル、チェーン、使っているオラクル、借入残高（USD）
- 過去 30 日の清算の件数、返済総額、粗利の推定。ledger に source がなければ足す
- 価格更新を誰でも出せるか（権限があるか）、更新 1 回の手数料
- 取り手の上位 3 運用者と占有率。それぞれの型（1 の分類）
- **取られるまでの秒数**: 「オフチェーンの配信価格が清算の線を越えた時刻」から「清算の tx が入った時刻」まで。配信価格の過去の値が、キーの要らない公開の所から取れる場合だけ測ります。取れなければ「測れない」と書いて、取り手の tx の間隔など分かる範囲だけを書いてください。測る事例は earner が、1 プロトコルにつき最大 10 件（粗利の大きい順に 5 件、小口から 5 件）
- farm に足りないもの: 価格配信を受ける仕組み、executor の「価格を更新してから清算する」入口、更新の手数料の分のネイティブトークン、など

Pull 型の bot は、今の farm では **C（farm にない仕組みが要る）** です。bot はまだ作りません。一覧がそろったら、meta が日本語で inbox/human に出してください（題は `pull-oracle-markets`）。秒数が farm の反応時間 R を超えている事例が、粗利の合計で 300 USD 以上（過去 30 日）ある所を先頭に並べます。価格配信を受ける仕組みを作るかどうかは、その一覧を見て人間が決めます。

## 3. 価格の線を前もって計算しておく（earner）

feed で価格更新を待つ bot を作るとき、または直すときは、次の形にしてください。

- 監視しているポジションごとに、**清算できるようになる価格**を前もって計算して持っておく。価格更新のイベントが来たら、その表と比べるだけで対象が決まるようにする（イベントが来てから全ポジションの状態を読み直さない）
- 表は、担保や借入が動いたイベント（預け入れ、返済、借入など）で更新する。数分おきの確認用のポーリングでも作り直す（decision 2026-11-13-next-block-feed の 2 のとおり）
- 利息の積み上がりで線を越えるポジションは、**越える時刻**を前もって計算する。越える前の最後のブロックで健全、次のブロックで清算可能、という事例が過去 30 日にあったかを数える（1 の T）
- 送る前の確認は executor に任せる（利益なしで revert）。bot の側で読み取りを重ねて遅くしない

これは作りの指定で、期待収益の数え方は変えません。reviewer は、feed を待つ bot がイベントのたびに全ポジションを読み直していたら fix にしてください。
