# Farm 仕様書（続き）

## 既知の落とし穴と対処（続き）

| 症状 | 原因 | 対策 |
|---|---|---|
| `paper archive <id>` が「bad arguments」 | 理由は `--reason` で渡す（`paper archive <id> --reason "<1 行の理由>"`）。内部の paper-ctl は位置引数 `archive <id> <reason>` なので取り違えやすい | 使い方の問題。コマンド集に追記。迷ったら `sudo -u harness /opt/farm/bin/paper help` |
| live レーンの Alchemy 消費が日次予算を超えても止まらない（11-10、moonwell で 1 日約 10M CU） | 設計どおり: live は常に Alchemy 優先で予算で絞らない（送信を止めないため） | 月間枠を使い切ると送信も止まるので、ブリーフで月の累計を見る（11b からブリーフの先頭に `alchemy this cycle` の行が出る）。50M を超えたら対策を相談。moonwell は 11-10 に人間が停止し、11-11 の decision で reviewer が promote 前に CU を見積もる運用にした |
| gate-ctl に同名メソッドが 2 つある / バンドルを置くときのサーバー側との差 | Project の farm/current の写しとサーバーのファイルが一致する保証がない | 9i から: ファイルの丸ごと置き換えではなく、文字列照合でパッチ（各箇所がちょうど 1 回一致しなければ何も変えない）し、旧版と新版の両方にオフラインテストを走らせる |
| （潜在、11-11 のコード監査で発見）relay がエラーやタイムアウトを返した送信が実際には届いていると、watchdog が「鍵の漏洩の可能性」で全 bot を halt・sweep する | watchdog は signer.log の `sent` と gate.log の成功記録の nonce しか既知としなかった。signer は RuntimeError 以外（ソケットのタイムアウト）では記録を残さず、gate の `sweep_failed` には nonce がなかった | 10e: signer はどの失敗でも nonce 付きの `broadcast_failed`、gate は `sweep_failed` / `cancel_failed` に nonce、watchdog はそれらも既知とする。どの記録にもない nonce は従来どおり halt |
| （潜在、同上）sweep / stop の途中で 1 チェーンの RPC が落ちると、先のチェーンの記帳が消え、次の sweep が「principal gone」で元本全額を損失計上。bot は archive されて残った資金が X と watchdog の外に | sweep は pnl.json を最後に 1 度だけ保存し、RuntimeError しか捕まえなかった。stop は sweep の成否を見ずに archive していた | 10e: sweep は例外でもそこまでを保存、失敗した送信を `sweep_unsure` に覚える、stop は未完なら archive せず終了コード 3（やり直せる） |
| （潜在、同上）累計損失 30 USD の停止が 1 回失敗するとそのまま。止めた ID を同じ名前で再 promote すると判定されない | watchdog の LOSS_STOPPED が、停止の成否にかかわらずプロセスの間ずっと ID を覚えていた | 10e: bot がまだ live にあれば 10 分ごとに再試行、live から消えた ID は忘れる |
| （潜在、同上）ガスを使い切った bot を止めても PnL に損失が出ない | sweep は送れる残高がないチェーンを「swept 0」で飛ばし、baseline との差を記帳しなかった | 10e: 空の wallet でも baseline との差を記帳して baseline を消費 |
| バンドルの展開で `tar: … time stamp … is … s in the future` | 10e のバンドルはファイルの時刻を 2026-11-11 00:00Z に固定して作った。サーバーの時計がそれより前だった | 害はない（警告だけ）。10f からは時刻を作成時点より前に固定 |
| promote が bot を live に移して資金を送った後、「executor artifact unreadable: … bots/paper/<id>/contracts/…」で停止（11-10 20:05Z、reserve-dutch-ethereum-v2） | manifest の `executor:` が bot 自身の paper ディレクトリ内の artifact を指していた。gate はディレクトリを live に移してから artifact を読むので、そのパスはもう存在しなかった（それまでの bot は artifact が scratch/ にあった） | 10f: artifact と引数は何も動かす前に読む。`bots/paper/<id>/…` のパスは移動後 `bots/live/<id>/…` で探す。止まった bot は `gate-ctl deploy <id>` で再開（実際に再開した） |
| `gate-ctl deploy <id>` が「already has an executor (state/executor.json)」と拒否するが、その bot の executor は未配備（同上） | archive した live bot を paper に戻すとき `state/executor.json` ごとコピーされ、前の bot の executor アドレスが残っていた。gate はファイルがあるかどうかしか見ていなかった。signer もそのアドレスを許可先に足す | 10f: アドレスがその bot の鍵と nonce から導いた値と一致するかで判定し、一致しないファイルは配備の前に消す |
| inbox/live にメモを置いても誰も処理しない | live-operator は常駐せず、watchdog が起こしたとき（failed・損失・不明な nonce）しか動かない。inactive / dead の live bot は「failed」ではない | 急ぐものは人間が gate コマンドを実行する。不要になったメモは `inbox/live/done/` に移す（残すと次に起きた live-operator が古い依頼を実行しうる）。running でない live bot は 11b からダッシュボードの「要確認」に出る |
| （潜在、10g で発見）arbitrum の bot への資金移動や sweep が「intrinsic gas too low」で失敗しうる | gate は送金のガスを 21,000（USDC は 90,000）に固定していた。Arbitrum Nitro は親チェーンへの投稿コストをガスに上乗せする。arbitrum に bot を出したことがなく表に出ていなかった | 10g: Nitro のチェーン（arbitrum・elysium）では gate が `eth_estimateGas` × 1.3 を使う |
| 10g の install が preflight で「Temporary failure in name resolution」 | `FARM_ELYSIUM_ALCHEMY` に URL 全体（`https://elysium-mainnet.g.alchemy.com`）を入れた。install はその値を `https://<値>.g.alchemy.com/v2/<キー>` に埋め込む | 入れるのは `elysium-mainnet` の部分だけ。既定値がそれなので指定は不要。preflight で止まれば何も変わっていない |
| earner が 15 秒ごとに即終了し続ける。ログに `assemble-prompt: prompt for earner-local is 61377 bytes (max 60000)`（11-11） | 組み立てたプロンプト（common.md + roles/earner.md + TOOLS.md）が `/opt/farm/bin/assemble-prompt` の `MAX_BYTES` を超えた。dsh は指示を 64 KiB（65,536 バイト）までしか読まないので、その手前で止める作り。meta が役割ファイルと TOOLS.md に追記を重ね、10g の common.md の elysium の段落も加わって超過した（common 15,978 + earner 21,298 + TOOLS 24,097 バイト） | 一時対処として `MAX_BYTES` を 64000 に（11-11、人間がサーバーで直接変更。バックアップ `.assemble-prompt.bak-20261111`）。本筋は meta が earner 向けの分を削ること（inbox/meta/2026-11-11-earner-prompt-over-limit.md で依頼、4,000 バイトの余裕を求めた）。65,536 は dsh 側の上限なので、これ以上は上げられない。common.md に段落を足すときは合計の大きさを確かめる。同日 19:42 JST の meta が 52,722 バイトまで削減（TOOLS.md 24,097 → 17,347、earner.md 21,298 → 19,393。詳細は wiki `infra/relay-reference.md` へ移動）し、`tools/prompt-size.py`（role ごとの組み立てサイズを表示、56,000 超で exit 1）を追加した。これを受けて `MAX_BYTES` は 19:58 JST に 60000 へ戻した。10k から: assemble-prompt は 56,000 バイトを超えると `inbox/meta/prompt-size-<instance>.md` を書く（harness として書く。大きさが変わったときだけ書き直し、56,000 以下に戻れば消す）。60,000 超で失敗するのは変わらず、そのときはメモに「起動できない」と書く。11b からダッシュボードとブリーフに instance ごとの大きさが出る |
| サーバー再起動の直後に live bot が全部落ち、start limit に達して live-operator が起きる（11-11 09:42Z） | rpc-relay は名前解決が使える前に「起動済み」になり、最初の上流呼び出しが失敗（`Temporary failure in name resolution`、続いてプロバイダを休ませている間の `no provider available`）。farm-signer は起動時のフィード検証が読めずに終了し 5 秒ごとに再起動。bot@ は signer を `Requires=` しているので、signer の再起動のたびに全 bot が再起動されて落ち、10 分に 5 回の上限に達した | 10j: rpc-relay を `network-online.target` の後に起動（drop-in `rpc-relay.service.d/network.conf`）、farm-signer に `ExecStartPre=/opt/farm/bin/relay-wait 150 ethereum`（relay が ethereum の `eth_blockNumber` に答えるまで最大 150 秒待つ。必ず 0 で終わる。drop-in `farm-signer.service.d/wait-relay.conf`、`TimeoutStartSec=200`）。bot@ は元から signer の後に起動する順序。signer を再起動すると live bot も一緒に再起動されるのは `Requires=` による仕様 |
| elysium の fork で reset 直後の eth_call が `Excess blob gas not set.`（11-11） | elysium（Arbitrum Orbit）のヘッダには excessBlobGas がなく、anvil（hardfork Bpo1）がフォークした先頭ブロックでの eth_call を拒否する。ローカルで 1 ブロック採掘すると直る | 10j: `fork reset elysium`（と `fork replay elysium`）は reset の後に `evm_mine` を 1 回送る。fork は指定したブロックの 1 つ先になり、replay は mainnet より 1 ブロック後で実行される。採掘に失敗しても reset は成功扱い（警告だけ）。再起動直後の fork は、最初の `fork reset elysium` まで同じエラーを出しうる |
| promote が bot を live に移して資金を送った後、「executor deployment on ethereum needs 3,190,399 gas, above the 3,000,000 …」で停止（11-11 20:39Z、morpho-watcher2-ethereum） | executor が大きすぎた（配備の見積もり × 1.2 が 1 tx の上限 3,000,000 を超える）。gate が配備ガスを事前に確かめるのは hyperevm だけで、他のチェーンでは移動と送金の後に `deploy_executor` が初めて見積もっていた | 10l: promote は全チェーンで、何も動かす前に見積もって拒否する。止まった bot は executor を配備できないので `gate stop <id>` で資金を戻す（`gate-ctl deploy` での再開は不可）。earner が executor を小さくして別 ID で出し直す |
| feed の `/head` の費用を約 3 分の 1 に見積もっていた（11-13、11a 適用時に判明。実害なし） | newHeads の通知を約 1,400 バイト（約 55 CU）と推測して設計したが、Alchemy の実物は 3,855 バイト = 154.2 CU だった。流し続けると 1 日 約 1.1M CU で、feed 全体の上限 700,000 CU を head だけで使い切り、その日は log の購読も止まる | install の `--check` が実測を表示して気づき、その場で feed.json の `heads` を `[]` にして無効化。meta 宛てメモと decision は実測値に訂正してから配置。購読の費用は推測せず、`--check` か `/health` の `cu_today` で測ってから決める |
| （潜在、11b の作成中に確認。未修正）ops.db / KB / ledger のテーブルが読めないと、brief.txt とページが 500 になる | farm-dash の 11b より前からの欄（Recent runs、RPC today、KB leads、ledger の実行履歴）は、sqlite のエラー行をそのまま表の行として扱い、KeyError になる。DB が壊れたときやテーブルがまだないときにだけ起きる | 起きたら `journalctl -u farm-dash` ではなくページの「dashboard error: KeyError(…)」を見て、どの DB かを当たる。11b で足した欄は読めない情報源があっても表示を続ける。直すなら既存の 4 箇所を同じ作りにする（未着手） |
| Project の文書（本書・運用記録・目録）の更新に時間がかかる | Project の文書は部分的な書き換えができず、全文の置き換えだけ。新しいチャットには 3 文書のファイルが手元にないので、全文を書き起こすことになる | 該当する文書を Project からダウンロードしてチャットに添付すると、該当箇所だけ編集して書き戻せる（添付した版が Project の最新と同じかを、編集の前に確かめる）。ただし、ファイルから書き戻すには、編集後のファイルを 1 回の読み取りで全部読めることが条件で、読み取りには上限がある。11-14 に各 約 130 KB の本書と運用記録を添付して編集したところ、日本語の多い運用記録は約 28 KB、英数字の多い本書は約 50 KB で読み取りが打ち切られ、書き戻せなかった。そのため同日、本書を 6 つ、運用記録を 8 つの文書に分けた（1 文書は 24 KB 程度まで）。文書が 24 KB を超えそうなら、新しい文書に分けて一覧に足す |
| earner が `failed (Result: start-limit-hit)` で止まる。セッションはどれも正常終了している（11-13 07:28 JST） | 作るものがない earner が 1〜3 分でセッションを終え、終了 15 秒後の再起動が 1 時間 20 回の上限（StartLimitBurst）に達した。きっかけは decision 2026-11-13-morpho3-stop-ev-net-of-gas の 4（作るものがなければ短く終えてよい）。モデルやプロンプトの故障ではない（LLM サーバーが落ちて即死する上の行とは別の原因） | `sudo systemctl reset-failed agent@earner-local` → `start` で復旧。drop-in `agent@earner-local.service.d/restart-delay.conf`（`RestartSec=300`、11-13）で次の起動まで 5 分にしたので、最大でも 1 時間 12 回で上限に当たらない。ダッシュボードとブリーフの Agents に `failed/failed` と出るので、そこで気づける |
